# 初始化 STDD 项目

1. 从请求确定目标目录和项目名。新项目优先使用用户给定的目录，只有项目名称时用同名子目录。已有代码、测试或已交付功能的项目，按[已有项目接入](references/existing-project.md)建立相关行为基线，再起草下一项变更。目标描述可省略，随后从任一角色补齐。
2. 选择最贴合任务的配置。通常用 `team`，同时安装角色入口、模板和通用研发技能与脚本。只搭产品设计或研发协作底稿时用 `spec`，保留四个角色的文档入口。需要可运行的教学示例时用 `demo`。保留用户已选的技术栈、现行规范及测试入口。
3. 使用本技能的 `scripts/init_stdd.py`。`--profile` 决定生成的项目内容，`--agent` 独立决定研发技能放在哪里。省略时分别用 `team` 和 `all`，为 Codex、Claude Code 和 Qoder 布置目录。用户指定工具时传相应选项，要求按安装位置识别时用 `--agent auto`。其他工具可使用 `--skills-dir` 或 `--agent portable`。首次接入已有目录时先用 `--dry-run` 查看将新增及保留的文件。只为已初始化项目接入新工具时用 `--skills-only`。命令和目录见 [使用说明](references/usage.md)。
4. 用户给了目标时，在新生成的 `docs/stdd/project.md` 和初始 `changes/<id>/` 中起草首个可验收切片。产品明确用户与范围，设计写影响的界面或交互状态，研发在 `tasks.md` 给出简短实施方案，测试写可观察的预期和验证入口。复杂变更可加 `--design` 生成技术设计。方案和验收口径确认后进入开发。若用户从某个角色切入，优先细化其有足够信息的部分。详细分工见 [初始化与交接](references/role-handoffs.md)。
5. 检查角色入口链接及首个变更的一致性。使用本脚手架现行规格格式时可运行 `python3 -B scripts/check_traceability.py`，已有项目按仓库约定验证。生成 `demo` 后运行 `make check`。报告目标目录、研发技能的实际路径、已生成和保留的内容、未决业务问题及验证结果。
