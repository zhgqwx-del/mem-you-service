# Git 基线 分支与提交前检查

将实际约定记在 `AGENTS.md` 或工程文档中。任务中已有明确要求时按其指定的基线和目标执行，随后把本次分支、基线 SHA、合入目标和选择原因留在变更记录。已有项目可沿用自己的 Git 流程。

| 约定 | 团队需写明什么 | 缺省行为 |
| --- | --- | --- |
| 开工基线和合入目标 | 每类任务的基线、本地或远端引用、目标分支 | 识别当前工作区和已有变更，不猜测其他分支 |
| 同步方式 | 远端、何时刷新引用、是否要求更新本地基线 | 使用已核对的本地引用 |
| 开发分支 | 使用当前分支、新分支或工作树，以及命名规则 | 保留当前分支 |
| 提交前检查 | 定向测试、构建、lint、全量检查及适用范围 | 使用仓库现有入口记录实际运行结果 |
| 提交整理与合入 | merge、rebase 或 squash 的位置和适用分支 | 保留现有提交历史，准备可评审的变更 |

使用短期功能分支的团队，可以在仓库约定里写「从 `origin/main` 建 `feat/<变更名>`，打开 PR 到 `main`，合入时由 PR 执行 squash」。使用发布分支的团队可以按任务类型列不同基线和目标。

## 开工

1. 检查 `git status --short --branch`，并解析实际基线和目标引用。若已有变更分支，复用其目标与对应记录。基线和目标不同，例如修复版本分支时，分别写清。
2. 仓库约定需要最新基线时，先 `git fetch` 已确认的远端，再从刷新后的引用取 SHA。需要推进本地基线时，按项目流程在正确分支上做快进更新。遇到分叉时按项目选定的合并方式处理。
3. 按约定复用或创建开发分支。需要隔离，且当前工作区已有改动时，优先考虑从选定基线建立独立工作树。保持原有改动与暂存区可追溯。仓库没有明确分支约定时，可在现有工作区先起草方案。
4. 交付可评审的实施方案。宿主支持规划模式时可以进入该模式，确认记录来自用户、需求负责人或团队已有的评审。

## 提交前

1. 核对真实的合入目标和候选分支。项目约定或用户明确要求 rebase 时，先核对干净工作区、基线引用和分支共享状态。共享分支的历史整理遵循团队约定及相应授权。冲突处理以已确认方案为准，保留冲突和当前 Git 状态供复核。
2. 按项目运行定向验收及适用的构建、静态检查、回归和手工验收。若更新基线引入依赖变化，先按项目方式同步依赖。记录实际退出状态、观察结果和受测提交或工作区状态。必跑检查失败时，在 PR 草稿标明当前状态。
3. 团队使用 squash merge 时，可在 PR 合入环节压缩提交。需要本地 squash 时，按项目约定及历史改写授权处理明确的提交范围。整理提交后核对最终候选与受测内容，内容发生变化时复跑受影响的检查。发布与推送遵循任务授权。
