# 已有项目接入 STDD

把 STDD 接到现有代码、测试和协作约定上。选用户指定的下一项变更，或从用户已明确的目标中提出最小的可验收切片。只要求接入时，先补齐协作入口，并把首个变更的目标标为待定。

## 1. 找到实际入口

- 读适用的 `AGENTS.md`、README、构建配置、现行规格和测试。找到本次涉及的公开入口、调用方和真实的构建测试命令。
- 有版本控制时记录当前提交和工作区状态。已有工单、变更或规格时沿用其编号与权威位置，核对已有的 `changes/` 目录和归档。
- 查看项目已有的讨论入口和 ADR 目录。若已有 `docs/adr/` 或 `docs/decisions/`，沿用已有记录、编号和索引。相关文件从本次 `change.md` 链接。
- 盘点本次切片涉及的行为、依赖与要保留的约束。代码、测试和规范出现分歧时，记录各自证据和待决定的口径。

## 2. 记录接入前的基线

从实际入口复核能观察到的行为，按现有环境执行相关检查。记录版本或工作区状态、命令、测试数据、实际结果和已知失败。缺少可运行环境或用例时，写明原因与复跑方式。将从代码推断的行为标为待验证，将有待决定的业务规则记录到 `change.md`。

将这份基线暂存在工作记录中，生成变更后写进该变更的 `verification.md`。注明它对应接入或修改前的版本。未来行为的验收场景保持待验证，已有的通过结果只作为现状证据。

## 3. 预览并补齐文件

使用 `team` 配置作为默认。如下示例从解压后的技能目录执行，目标路径和变更 ID 换成实际值。

```sh
python3 -B scripts/init_stdd.py /path/to/existing-repo \
  --change-id 010-message-retry \
  --change-title "消息发送失败后可重试" \
  --goal "允许发送失败后重试，接收方只看到一条消息" \
  --dry-run
```

检查 `CREATE`、`KEEP`、`UNCHANGED` 和 `BLOCKED`。核对范围后用相同参数去掉 `--dry-run`。生成器会保留已有同名文件。使用仓库现有的规格、测试和 CI 约定，按需为现有 README 或 `AGENTS.md` 补一条指向 `docs/stdd/project.md` 的导航。路径冲突时依据项目约定选入口，并在交付说明中列出仍受阻的内容。

已完成 STDD 接入，只需为新的编码工具补技能目录时，使用 `--skills-only` 并选择所需 Agent。参数及现有文件处理见[初始化器用法](usage.md)。

## 4. 起草并交接首个变更

- 在 `change.md` 写明当前行为、目标行为、要保留的行为及待决定事项。在变更 `spec.md` 将明确的预期写成 `REQ` 与 `AC`，以草稿交给对应负责人评审。
- 在 `test-plan.md` 写可观察的结果、测试数据和实际执行入口。在 `verification.md` 保留接入前基线，与本次实现后的验收结果分别记录。
- 在 `tasks.md` 写实施方案的修改位置、关键取舍、验收方式及确认记录。复杂变更补 `design.md`。核对生成和保留的文件、角色入口、测试命令和待确认问题。方案和验收口径确认后，用 `stdd-delivery` 写测试、复核旧实现与目标的差异，再实施。角色分工见[四角色交接](role-handoffs.md)。

例如，已有单聊的项目接入「发送失败可重试」时，先找消息发送入口及已有测试，记录当前重试时的观察结果。等待负责人确认消息标识是否沿用、接收方怎样判定重复，再把确认后的行为写成可复跑用例。
