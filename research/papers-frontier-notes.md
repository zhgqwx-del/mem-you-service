# Agent 记忆论文与前沿：面向中文个人记录服务的研究笔记

查询日期：2026-10-26（America/New_York）。研究范围：论文、作者项目页和作者仓库；不以厂商营销榜单或第三方解读作事实依据。本笔记区分“论文做了什么”与“本需求下的工程推论”。没有运行论文实验，论文的结果均不能视为本地复现。

§1–10保留上述日期的研究快照，不替代docs/spec-v1的现行接口、职责和检索策略。2026-10-28补核上下文退化与GRPO/Agentic RL，见§11；Hy-Memory资料另见targeted-gaps-notes§6。

## 1. 可用于决策的结论

1. **本需求的核心问题是“收到一条新记录后，哪些历史值得交给 Agent”，与显式历史问答不同。** `今天又胃胀了` 并不直接告诉系统该查哪些食物、时间段、前次处置或用户沟通偏好。检索输入应是当前事件、近期上下文及可能影响回复/工具/澄清的需要，而不只是原句向量。
2. **先建可追溯的外部记忆服务，模型原生记忆作为后续研究方向。** MemT-1.0 确实是已发布的项目，但它要求特定模型和有状态推理栈；它的固定容量潜在状态不适合承担精确账目、体重序列、用户纠错和可审计事实的唯一副本。
3. **结构化账本与自由文本都需要。** 数量、单位、时间、事件状态应能确定性查询；原文及上下文负责保存“说的究竟是什么”。纯摘要与纯向量都容易丢失此区别。
4. **把“相似”与“有帮助”拆成两个阶段。** 先广泛召回，再判断能否改变这次交互；允许空结果。情绪低落时，最相似的负面经历未必是最合适的支持材料。
5. **记忆管理操作要成为显式协议。** 添加新事件、补充旧事件、纠正事实、更新当前状态、关闭待办/未完事项与删除用户数据是不同操作，不能统一为向量相似度驱动的 UPDATE。
6. **巩固/反思应生成可撤销的派生视图。** 原记录提供证据，周期摘要与模式描述提供便捷索引；派生结果应保留来源和版本，避免生成结果反复回写为新事实。
7. **不要从论文胜率推导产品胜率。** 数据集语言、历史生成方式、读取原文权限、抽取/回答模型、token 预算、裁判、样本集版本都会改变分数；应在相同成本预算下比较实际 Agent 行为。
8. **MVP 的学习目标应先是“判定有用、准确更新、少打扰”，不是训练记忆基础模型。** 先记录收益和错误样本，后续再用监督训练或偏好优化训练轻量 reranker/门控；端到端 RL 需要可靠反馈才能成立。

上列为针对本产品的综合工程判断，依据见以下论文；并非任何一篇论文已经验证的完整方案。

## 2. 技术范式地图

## 3. MemT 1.0 身份核实与适配判断

### 3.1 确认的身份

用户所提名称可以对应 **MemTensor 团队的 MemT-1.0: Towards Memory-Native Evolution**。论文初次提交为 2026-10-19，当前 arXiv 为 2026-10-20 v2，作者仓库为 `MemTensor/MemT-1.0`。本次未发现需要另选同名项目的证据。[论文与版本记录](https://arxiv.org/abs/2610.26825)、[作者仓库](https://github.com/MemTensor/MemT-1.0)。

### 3.2 技术机制

它将 Native Memory Block 接到骨干 attention 旁：Local Memory 是每条交互轨迹独立的动态矩阵；Hyper Memory 是经训练的读写投影和门控参数。当前 step 从进入时的记忆快照读取；本轮结束后，用稳定化的 GDN-2 token 级更新累积输入与输出。Mixture-of-Storage 用多个存储专家和读/写路由扩展容量。在线运行固定共享权重，变化的是每轨迹记忆状态；固定配置下，状态大小不随该轨迹历史长度增长。作者也明确指出固定容量会损失细节，长历史上的显式文本证据系统仍有优势。[技术报告 §2、§4.3、§6.2、§8](https://arxiv.org/html/2610.26825v2)。

不要把“训练记忆投影”误解成“每条用户记录都更新模型权重”，也不要把矩阵的 erase/forget gate 当作一条指定用户事实的可验证删除。这两个说法都超出了报告能够支持的语义。

### 3.3 服务与许可边界

作者推理实现提供会话、独占 lease、事务 publish/abort、快照 export/import、reset/close；用专用 session 协议驱动 SGLang。文档当前要求特定 BF16 checkpoint 和受限的 eager 推理配置。说明它有服务端工程实现，但外部任意模型不能直接读取其潜在状态。[推理 README](https://github.com/MemTensor/MemT-1.0/blob/main/inference/README.md)。

仓库 README 明确：原始软件采用 **PolyForm Noncommercial 1.0.0**，商业使用需要另行授权；报告采用 CC BY-NC-SA 4.0，权重/数据/第三方材料条款另计。应称为“公开代码的研究项目”，不能仅凭 GitHub 可见就将其视为可直接商用的宽松许可组件。[作者许可说明](https://github.com/MemTensor/MemT-1.0#%EF%B8%8F-license)。

**适配推论：** 可作为长远探索的第二记忆通路，例如低成本偏好概括或程序性经验压缩；但给任意 Agent 服务时仍应输出可核对的文本与结构化证据。若把 MemT 作为“代记忆模型”再生成文本供其他 Agent 用，需要额外推理、事实忠实度和证据定位验证，不能直接宣称已解决独立记忆服务问题。本次未验证其中文个人记录效果、原子删除、跨 checkpoint 状态兼容或生产多租户保障。

## 4. 关键源头：应借鉴的机制与边界

### 4.1 MemGPT（2023；论文 v2 为 2024）

机制：把有限上下文视作内存，外部召回/归档存储视作磁盘；主上下文包含固定指令、可写 working context 和 FIFO 消息队列。模型通过函数调用读取/修改记忆，队列管理器在压力下生成递归摘要并驱逐旧消息；原始消息仍可分页搜索。`request_heartbeat` 支持一轮交互内多次检索。论文测试长期聊天及文档检索，效果也依赖底座模型是否愿意继续查找。[论文 §2、§3](https://arxiv.org/html/2310.08560)。

**适配推论：** 独立服务可返回小型常驻用户状态与事件相关证据，并保留 `search/get` 工具补查。不要让首次接入的 Agent 必须实现整个 MemGPT 调度器；“模型主动决定何时查记忆”有漏查风险，记录请求可由 hook 先触发一次服务端 recall。递归摘要不能成为唯一事实库。

### 4.2 Generative Agents（2023，UIST）

机制：自然语言 memory stream 保存观察；retrieval 合并语义相关性、按上次访问时间衰减的 recency、LLM 评定的重要性；反思把事件提升为高阶认识，反思也可再次检索。论文环境是 25 个模拟角色的小镇，评估目标包括行为可信度和社会行为，不是个人健康账本的数值准确性。[论文 §4、§6–8](https://arxiv.org/html/2304.03442)。

**适配推论：** “当前情境检索历史”非常贴近新记录触发。但不能照搬其 importance：早餐在故事模拟中是小事，在饮食记录中可能是核心数据。recency 应根据事件发生时间、变化速度、领域和使用目的设置；按“被检索次数”不断强化可能形成反馈偏差。

### 4.3 MemoryBank（预印本 2023，AAAI 2024）

机制：保存对话并生成层级事件摘要、用户理解；用语义检索取历史；采用受遗忘曲线启发的简化衰减，召回会增加记忆强度并重置计时。作者明确该遗忘模型是探索性的简化。SiliconFriend 是长期陪伴应用，实验含模拟对话与定性用户案例。[论文 §2–4](https://arxiv.org/html/2305.10250)。

**适配推论：** 可以衰减一条记忆进入上下文的优先级，但不应因“不常被提起”删除用户原始记录。罕见过敏信息可能长期重要；天天重复的体重记录也不是应被合并掉的重复事实。陪伴感、检索价值与数据保留应分别制定策略。

### 4.4 A-MEM（2025，NeurIPS；当前 v11 为 2025-10-08）

机制：每个原子笔记记录原文、时间、生成的关键词/标签/上下文解释、embedding 和关联链接；新笔记先寻找相关旧记忆，再用 LLM 建链并更新旧笔记的语义描述；检索可扩展到相关链接。论文是对记忆组织和表示演化的研究，不等价于任意成熟图数据库。[论文 §3、§6](https://arxiv.org/html/2502.12110)、[作者系统仓库](https://github.com/WujiangXu/A-mem-sys)。

**适配推论：** 对 `又这样了`、`71.4` 等短句，适量语义丰富化和事件关联很有价值。但应将原文与生成解释分字段存储，解释附来源与置信度；不能让自动补充的病因、财务动机或人格判断成为用户陈述。关联视图可改，原始记录不可悄悄改写。

## 5. 记忆策略学习与巩固：哪些可落地

### 5.1 Memory-R1（2025；当前 v5 为 2026-01-14）

将 Memory Manager 与 Answer Agent 分开：前者对新信息及检索出的旧条目选择 ADD/UPDATE/DELETE/NOOP；后者从候选记忆提炼相关内容回答。以最终 QA 正确性作奖励，用 PPO/GRPO 训练；测试包括 LoCoMo、MSC、LongMemEval。它证明记忆操作策略可以学习，而不是必须永久依赖固定提示词。[论文 §3、§4](https://arxiv.org/html/2508.19828)。

**适配推论：** 初期可先模仿其操作显式化，并收集“应该新建、补充、纠正还是不变”的真实样本；不要直接照搬其 DELETE 语义。个人记录中 `今天 71.4` 与 `昨天 71.8` 是两次观察，`刚才其实是 71.6` 才可能是纠错。QA 奖励没有直接覆盖沟通打扰、心理支持适配、用户删除要求或未知未来用途。

### 5.2 Mem-α（2025-09-30）

训练写入 Agent 按 chunk 累积信息，在 core、episodic、semantic 三种外部组件上使用工具；以 QA、格式、压缩和记忆内容奖励优化，使用 GRPO。实验含较训练序列更长的输入，但这是指定任务分布和工具接口下的结果。[论文 §3–4](https://arxiv.org/html/2509.25911)、[作者代码与处理后数据说明](https://github.com/wangyu-ustc/Mem-alpha)。

**适配推论：** 可借鉴“存储收益受预算约束”的目标；不能把压缩率作为主指标。中文个人记录中，恰恰有未来不可预知、当时不起眼的细节。学得的策略应更新派生层，不能越过保留原始证据、数值一致性、用户撤回等服务约束。作者使用的处理后 MemoryAgentBench 也不能与原始版混报。

### 5.3 Sleep-time Compute（2025-04-17）

在问题到来前，先对已知上下文推理、生成可复用中间结果，再在多个后续问题间摊销。论文主要在改造后的数学任务及软件工程案例上验证；效果依赖未来问题的可预测程度。它是计算时机设计，并不要求模型在“睡眠”中修改参数。[论文 §3–7](https://arxiv.org/html/2504.13171)、[作者仓库](https://github.com/letta-ai/sleep-time-compute)。

**适配推论：** 适合后台计算近期事件摘要、精确统计和仍未解决的事项；对所有用户每天做多层自由反思未必划算。任务应按活跃度、变化量和可复用性触发；评估必须计入后台 token、重算、过期缓存和长时间未再使用的浪费。

## 6. 与“收到新记录时给有用历史”更贴近的新研究

### 6.1 ENPMR-Bench（2026-05-26 v1；Findings of ACL 2026）

研究情绪需求感知的主动记忆检索：从当前表达推断潜在需要，选出对支持性回应有帮助的历史，而非只找同主题片段。数据由结构化用户画像、记忆与情绪支持场景生成并经筛选，理论框架使用 Maslow 需求映射；超过 1,800 条带记忆对话。[论文](https://arxiv.org/html/2605.27240)、[作者仓库](https://github.com/xingqwq/ENPMR-Bench)。

**适配推论：** `今天很挫败` 可能需要用户过去认可的支持方式或成功经验，不一定需要更多“挫败”的相似片段。可把“对这次回应的作用”加入 reranker。但该需求映射不能当成已证实的心理诊断；合成支持性对话和真实长期满意度之间仍需用户评估。

### 6.2 OP-Bench（2026-01；当前 v2 为 2026-09-26）

将过度个性化分为无关记忆使用、重复和迎合，构造 1,700 个验证样例。v2 HTML 正文及当前作者仓库强调已有后处理缓解有限，且可能损失正常个性化。范围主要是基于长期历史构造的单轮英文文本，作者明确列出语言、文化与多轮互动限制。arXiv 页面注明获 EMNLP 2026 接收。[明确版本正文](https://arxiv.org/html/2601.13722v2)、[作者仓库](https://github.com/yulinlp/OP-Bench)。

**适配推论：** 不能把“历史总能提一句”当作体验优势。服务应允许不返回记忆、只返回私下行动约束而不要求 Agent 显式提及；需要记忆被引用/已解决状态，以及用户希望简短回复、避免追问等交互偏好。

**官方材料不一致：** 最后复核时，arXiv 摘要页仍描述提出 Self-ReCheck，而明确 v2 HTML 和当前仓库强调后处理能力有限；不能简单断言摘要页已经同步。这里按具体正文和仓库归纳机制，不作“Self-ReCheck 已解决问题”的结论。仓库当前也未声明软件许可，代码复用需另核对。[摘要页](https://arxiv.org/abs/2601.13722)。

### 6.3 MemoProAgent / MemoProBench（2026-10；v2 为 2026-10-21）

**版本注意：** 同一 arXiv 初版名称为 ProPerAgent / ProPerMem，最新版已改名。其任务是从第一人称视频情境和长期个人记忆中，决定何时做有证据的主动提醒。方法以对象实体召回 episodic/semantic 图记忆，扩展图邻居和 PageRank；LLM gate 过滤不足以触发介入的证据，可返回空；训练奖励同时鼓励正确沉默并惩罚错误时机/重复提醒。[最新版论文 §3、§5](https://arxiv.org/html/2610.22671)、[作者仓库](https://github.com/facebookresearch/Memo-Pro-Agent)。

作者仓库当前仅覆盖推理/评测等首发内容，说明 histories 数据仍需获授权的 Hugging Face 访问；代码为 CC BY-NC 4.0，视频与数据另有条款。公开仓库不等于全部复现材料已可直接取得，也不等于可以直接商用代码。[仓库复现与许可说明](https://github.com/facebookresearch/Memo-Pro-Agent#data-and-reproducibility)。

**适配推论：** 可以转化为“新记录 → 候选历史 → 有用性门控 → 允许的交互建议”，尤其保留 unresolved/open-loop 状态。视频的时间窗口指标不能直接套到聊天；用户已经主动发来记录，也不等于允许任意扩大话题。可借鉴门控与负例，而不必首先引入图数据库或 RL。

### 6.4 VitaBench 2.0（2026-05-26 v1）

将同一用户的任务按时间组织，偏好分布在异质碎片交互里；要求持续提取、使用、更新偏好，并在缺信息时主动询问或访问环境。提供可替换的 update/retrieval 记忆接口。作者明确偏好和历史为程序化构造，基于任务轨迹的 rubric 也不覆盖开放用户满意度。[论文 §3、§5](https://arxiv.org/html/2605.27141)、[论文指向的作者仓库](https://github.com/meituan-longcat/VitaBench-2.0)。仓库标注 2026-06 发布 2.0、英文版尚待发布；不能将原 VitaBench 在 2026-01 的 ICLR 接收消息移作 2.0 的接收日期。

**适配推论：** 这比孤立历史 QA 更能启发服务接入评估：记忆正确找到之后，Agent 是否据此选择正确工具或避免无效追问仍要单独测。不能只测最终回答，也要检查过程中是否错误修改记录、过度询问或忽略更新后的偏好。

## 7. 评测体系：用公开 benchmark 校准，用自有任务定方案

### 7.1 值得保留的公开基线

| 基准与年份 | 主要测什么 | 对本服务有用的切面 | 不应外推之处 |
|---|---|---|---|
| [LongMemEval，2024/ICLR 2025](https://arxiv.org/html/2410.10813) | 500 个问题；信息提取、跨会话、时间、更新、拒答；区分 indexing/retrieval/reading | 时间归一化、多粒度索引、事实增强检索键、未知时不编造 | 用户显式提问，不能直接度量新短记录下的主动支持 |
| [LoCoMo，ACL 2024](https://snap-research.github.io/locomo/) | 人设与事件图驱动生成、人审的多会话对话；QA、事件摘要、图文对话 | 人物归属、跨事件与时间关联、证据召回 | 模拟人与人长对话不同于中文独白式流水账；不同论文也常选不同 QA 子集与评分 |
| [ConvoMem，2025-11](https://arxiv.org/html/2511.10523) | 75,336 QA，用户/助手事实、拒答、偏好、变化和隐含关联；长上下文与 RAG 成本交叉 | 冷启动及小历史量下，应认真保留全量/近全量阅读基线 | “前 150 对话无需 RAG”是实验条件下的经验观察，不能当生产硬阈值 |

### 7.2 本项目应该新增的评测（工程建议，非既有论文结论）

构建**以用户为单位、严格时间切分的中文交互集**。每个样本含：历史前缀、新记录、当时可见的近期上下文、允许的下一步行为、可用证据集合、不能推断之处。先用脱敏人工案例加合成扰动建立首版，再用知情同意的真实轨迹检验，保留完全未参与提示词调优的用户集合。

建议覆盖：

- 极短输入与指代：`71.4`、`又来了`、`还是昨天那个位置`；应正确关联或明确缺信息。
- 同领域不同事实：每次体重/饮食/症状/支出均需保存；相似不是重复。
- 补录与纠错：昨天发生、今天补录；“金额多写一个 0”与“又买一次”不同。
- 时间与状态：过去有某习惯、现在已改变；疑似过敏与确诊；曾经的症状与当前状态。
- 跨域候选：新症状与近期记录的饮食/用药/睡眠可能有关，但只返回事件共现证据，不替用户确认因果。
- 助手承诺与真实事实：Agent 说“我会帮你记录”不能算一条已经完成的记录；工具成功结果才可作为执行证据。
- 不应该用记忆：普通打卡只需确认；没有足够历史；用户不希望分析；相关历史已多次提及。
- 撤回与隔离：被删除的原文、embedding、摘要、缓存不能再被召回；另一用户和越权 Agent 的数据不得出现。

### 7.3 指标应分层

1. **写入层**：事件/数值/单位/时间字段正确率；错误合并率；纠错正确率；来源可追溯率；写入幂等。
2. **证据层**：必需证据 Recall@预算、上下文 precision、错误用户/人物归属率、过期事实率、时间约束错误、空结果正确率。
3. **使用层**：带/不带记忆的 Agent 对照，下一步回复/工具/澄清是否改进；错误追问、重复提及、无依据因果、过度个性化。
4. **系统层**：前台 p50/p95 延迟、前台与后台总 token/成本、索引新鲜度、删除传播时延。不要以低读取成本掩盖高抽取/后台巩固成本。

Recall@10、QA 准确率、LLM judge 分数和真实用户满意度是不同指标。固定召回条数也不公平：长 session 与短事实的 top-10 消耗差异很大，宜同时报告实际 token 预算。检索离线评测与端到端行为评测都应包含“没有记忆”对照。

## 8. 面向独立服务的落地推导

以下是基于研究的产品/工程建议，而非论文复述。

### 8.1 保存层与索引层分离

建议至少形成五类对象：

| 对象 | 示例 | 写入规则 |
|---|---|---|
| 原始事件 | 用户原文、工具返回、发送时间、发生时间 | 可追溯、可删除，保留输入权限；不因衰减自动丢弃 |
| 结构化观察 | 体重 71.4kg、餐费 32 元、主观症状 | 可带不确定/待澄清值，不能自动填未知单位 |
| 当前断言/偏好 | 最近减少咖啡、希望少追问 | 有有效期和来源；当前状态可更新，旧状态仍可按历史查 |
| 未完事项 | 三天后复查、上次问到的问题尚未补充 | 有 open/resolved/cancelled 状态，避免过期反复提醒 |
| 派生视图 | 一周摘要、模式假设、检索标签 | 带证据集合、生成版本、过期/失效规则，可重建 |

每个可用事实应能区分：用户陈述、设备/工具观察、Agent 推断、第三方陈述。`subject_id` 也不能默认为 user：用户可能记录家人身体、朋友借款或宠物饮食。`event_time`、`recorded_at` 与事实的 `valid_from/valid_to` 各有用途。可增加系统知悉时间支持补录/纠错的历史回放，不必在第一版就上完整图数据库。

### 8.2 新记录召回流程

1. 确定租户、用户、调用 Agent scope 和本次可用领域；先应用权限与删除过滤。
2. 将新记录解析为轻量 cue：主体、事件类型、实体、数值、时间、指代、明显更新/纠错信号；用有限近期事件补足上下文，不强制生成长画像。
3. 并行召回：近期窗口；结构化同类最新值/时间序列；精确词与实体；语义候选；相关未完事项与当前偏好。小库保留全量 rerank 的能力。
4. 合并、去重并补回必要原文；已被新断言取代的旧状态按用途区别处理，不能简单全删。
5. 在 token/延迟预算内判断“是否能改善这一次交互”；为返回条目赋用途：指代消歧、避免重复问、工具参数、最新约束、时间比较、待澄清冲突、可选情感支持。允许返回空列表。
6. 返回 Memory Context 包，附来源与时间、确定性、冲突/缺失字段、简短“为什么此刻有用”。最终回复和是否工具调用由 Agent 决定。

### 8.3 示例：`今天又胃胀了`

可返回：上次同类症状的发生时间与用户原话；用户当时自行记录的处置及后续反馈；近期少量有时间重叠的相关记录；明确的沟通偏好或待补充的症状信息。不要直接返回整个健康画像，也不应输出“牛奶导致胃胀”这样的新因果事实。

服务可以说 `过去 7 天有 2 条相似主观症状记录（证据 E12/E19）`，前提是查询口径完整；如果只有语义 top-k，就只能说 `检索到 2 条相关记录`，不能把召回结果数量冒充真实发生次数。

### 8.4 学习路线

首版采用可解释规则、成熟 embedding/关键词融合检索与一个受限 rerank/门控调用。先记录每条候选是否被使用、是否真正有帮助、用户纠正以及不该出现的历史；不要把“Agent 引用了”直接标为有用，因为 Agent 也可能被错误记忆诱导。

有足够标注后，优先训练三项小策略：候选有用性排序、冲突/追加/纠错识别、空返回门控。再判断是否需要跨阶段 RL。数值一致性、访问权限、删除传播和操作幂等始终由服务约束保障，不交给学得策略自由决定。

## 9. 实验优先级与未解决问题

| 优先级 | 对照实验 | 需要回答的问题 |
|---|---|---|
| P0 | 近期原文 vs 近期原文 + 结构化时间查询 | 单靠近期上下文是否已经足够，多大历史开始遗漏关键材料？ |
| P0 | 原文向量 vs 词法/实体/时间/语义融合 | 中文短记录、数字、否定、指代的实际增益是多少？ |
| P0 | 总返回 top-k vs 可空的有用性门控 | 少打扰是否能在保留收益的同时减少无关/重复历史？ |
| P0 | 最新状态覆盖 vs 事件追加 + 断言版本 | 纠错准确性与历史完整性能否同时满足？ |
| P1 | 仅原文 vs 原文 + 派生摘要/标签 | 丰富化增加多少召回，产生多少虚构或误归属？ |
| P1 | 即时抽取 vs 轻同步路径 + 异步巩固 | 前台响应、记忆新鲜度与总成本如何平衡？ |
| P2 | 手写策略 vs 有监督小策略 | 实际反馈是否足够稳定，训练能否跨用户和 Agent 泛化？ |
| P2 | 普通外部记忆 vs 原生潜在记忆辅助 | 在许可、资源、忠实度均满足后，是否存在明确成本收益？ |

仍需本项目自己解决的事项：

- 中文口语、单位省略、补录时间、否定、家庭人物和跨记录指代，没有现成 benchmark 自动保证。
- “有用历史”往往取决于 Agent 能执行的工具和当前产品体验，服务必须知道有限的调用意图/能力信息。
- 模式和人格推断的真实性、时效性和用户接受度，不能由 embedding 或 LLM 自评置信度替代。
- 论文通常无法保证删除传播、备份策略、多租户隔离、并发修订、长期漂移和实际可观察收益。
- 数据越长并非越该回忆；回忆错一次的成本与遗漏一次的成本因健康、财务、情绪和纯生活场景不同，需要领域化阈值及反馈。

### 11.1 对当前方案的有限吸收

以下为本项目工程推论，落实位置是04§6.4及00§4.5，不是上述论文已经验证本服务：

1. **将召回和reader用证据分开测。** 固定任务与正确证据，变化授权内无关内容、同主题干扰和重复片段，核对关键证据是否入模，以及入模后是否仍用错。仅报recall无法定位后一种失败。
2. **同时记录Memory预算与总上下文。** 聊天历史、工具结果、当前输入也占上下文；1200/4000是本服务数据预算，不能作为主Agent总窗口。用合法预算及固定代表场景画质量/成本曲线，不因文献直接提高上限或强制摘要。
3. **位置实验保留权限与快照语义。** 证据位置与可信任务说明位置分别控制，每个变体是独立可追踪输入/合法新包；不能改canonical_injection却沿用旧hash，也不能把历史原话变为system指令。
4. **维护历史污染负例。** assistant自述、旧工具结果、重复摘要和已更正主张不能成为新的用户事实；删前内容不为了测试“长上下文”而被合法重新注入。服务拒旧包、消费者reset及reader误用分别归因。
5. **学习策略保持后置。** 有合法数据与可靠标签后可研究写入候选、有用性、补查/澄清和预算策略；先固定reader/retriever，再隔离比较writer，避免只因reader更强而宣称记忆写得更好。QA答对、引用过或用户未纠正都不是充分的正确来源标签。

RL收益须与证据支持、工具目标、少打扰、存储增长、延迟和实际费用一起评价。权限、可信来源、CAS/幂等、连续屏障、人工保护、erase/撤权及消费者清理始终由协议强制执行，不能作为“扣分后可违反”的奖励项。训练权重不等于可按source精确删除的外部记忆；若将来使用用户轨迹训练，需另行设计授权、保留和删除边界。本次不启动数据收集、训练或真实模型调用。
