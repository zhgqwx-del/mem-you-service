# 调用链与设计完备性补充审阅

日期：2026 年 10 月 26 日。基于现有 README、技术方案、《05-记忆层设计》及 agent-service 参考接入的静态阅读。本文不证明服务已实现、外部框架已实测或生产门禁已通过。

§1–4保留上述日期的审阅快照，其中“尚缺合同”等描述不代表今天状态；现行开发依据为docs/spec-v1。2026-10-28对桌面原设计重新核对的来源证据、吸收情况与取舍见§5。

## 1 结论与新增边界

现有材料已达到“可启动受控原型”的架构深度，尚不是可直接照单上线的详细设计。已有方案已经写清来源版本、事件与观测、纠正删除、连续处理水位、即时覆盖、授权 scope、证据包、受控统计和评测；这些不应再次包装成新发现。

用户新明确的主调用链是：**产品发送 → 通用记录型 Agent → 独立记忆服务**。现有方案 §6.2、§6.3 将业务后端预取作为默认接法，应据此调整部署位置：把强制预取适配器放在 Agent 服务的可信请求编排层，在首轮模型推理前调用记忆服务；模型再通过工具补查。预取发生在模型前，与它属于 Agent 服务内部并不冲突。

仅提供 MCP 工具不能保证每次记录都调用记忆；让语言模型每轮先决定是否调用工具，也会增加一轮推理。不同 Agent 可提供两档接入保证：有生命周期适配器时保证每轮做受控的 context 决策；仅能安装工具时按需调用，不承诺每轮预取。独立服务协议保持一致。

现有 agent-service 的 `examples/record-assistant/reference.ts:124–159` 在调用方读取既有业务记录后组装 turn 输入；它是合成后端参考，不能证明 Agent 内动态记忆已经实现。当前 `memory-injection` 配置类型仅有静态 prefix/append（`packages/core/src/hooks/lifecycle-types.ts:80`），中间件固定注册表和实现也没有远程动态查询（`packages/core/src/hooks/middleware.ts:6,226`）。

## 2 原型开始前应补的具体合同

| 优先级 | 真正新增的缺口 | 需作出的决策与最小验收 |
|---|---|---|
| P0 | Agent 内部的编排位置 | 明确哪一可信组件保存新输入、调用 context、注入首轮输入以及发出工具；动态 hook 尚不可用时，在 Agent 应用编排器实现，不能把静态 prefix 配置当远程 hook。画出一条真实时序图并接一个 FakeMemoryProvider。 |
| P0 | 用户消息与产品正式记录的提交关系 | 新请求可能是新记录、查询、补充、更正或非记录对话。先可靠接收原始输入并不代表已生成体重、饮食或账目等正式条目。明确输入信封、业务条目、memory 来源分别归谁；同一消息含多个事件时用稳定的来源/动作/条目 ID 关联。 |
| P0 | 工具执行与记忆回流 | 哪些字段由 Agent 作为候选提出、哪些由业务工具确认提交；只有成功回执和明确用户陈述才能形成相应事实。提交成功但回复中断时不得重复记账；提交失败时不得在回复或记忆中声称已完成。检索返回的旧证据不得再当新来源摄取。 |
| P0 | 用户可见的状态语义 | 至少区分“原始输入已接收”“条目已保存/待补充”“分析完成/降级”。原方案已要求保存和分析分离，但需要落到实际请求和页面状态，防止输入落盘就亮出“账目记录成功”。 |
| P0 | 服务故障的决策矩阵 | 明确超时、限流、权限不足、版本落后、部分结果和修订待确认时，哪些轮次可以用当前输入继续、哪些必须追问或暂停相关工具；缺记忆不能解释为历史为空。保存通路与记忆分析故障分开。 |
| P1 | “忘记”的不同产品动作 | “不要再提”“不参与个性化”“删除这条记录”“删除所有记忆”不是同一操作。定义原文、产品条目、派生记忆和活跃会话的作用范围，并对需要消歧的自然语言请求给出可确认对象。 |
| P1 | 任意 Agent 的能力与授权合同 | 固定 SDK/REST 语义，MCP 只作工具适配；明确凭证授予和撤销、支持的生命周期、幂等能力、内容和超时上限。工具模式不能默许拥有 hook 的保证。 |
| P1 | 端到端运行证据 | 当前文档列出指标但未给目标或验证结果。先记录保存、首轮 context、异步富化、删除可见性及每次请求总费用，按预计用户规模测并发、冷缓存、积压与进程重启；未通过这些验证前只称原型。 |

这几项的关键是把已有原则具体化为运行合同，并非再增加一层“大记忆框架”。API JSON Schema、错误枚举、持久 operation 状态和真实接入实现尚未交付。

旧文值得借鉴的是职责分层、预取加工具、版本化富化、真实评测与可观测性。将它概括为“只有错误、无需参考”会损失有价值的工程经验；反过来，旧定价、benchmark 争论、固定冷启动条数与周更画像的强约束也不应成为当前项目要求。

## 4 进一步研究的优先级

1. **优先补产品调用闭环与数据权威性。** 用真实产品中的“一次发送包含多个事项、一次更正、一次纯查询、一次保存成功但回复中断”画时序并形成合同。这比再读十个 Agent 的 memory 源码更能降低当前风险。
2. **验证中文碎片记录中的上下文关联价值。** 固定 reader 和预算，比较无记忆、近期窗口、混合检索、混合检索加有限结构化观测；同时度量必要追问、重复提问、工具参数与不必要提及。
3. **按同一来源模型对照一个完整现成系统。** 先挑 Hindsight 或 Mem0 中一个做最小适配；评估中文效果、写入/读取调用数、更正即时性和删除传播。此时再决定第二个框架是否能回答新的选型问题。
4. **多模态与精确领域按实际 demo 的首发范围补。** 若输入有图片或语音，区分原始资产、模型描述和已确认事实，保存来源版本；若首版做饮食营养或财务分类，另验字段 schema 与错误代价，不能当纯文本检索自然附带的能力。
5. **图、策略学习、模型原生记忆后置。** 当前材料对这些方向已足够支持先不采用的决策；只有明确的关系查询或长历史收益问题出现后才值得加深。

只增加论文或仓库数量不能使方案完备。第一阶段缺的是约束清晰、可执行且能失败恢复的记录→记忆→Agent→业务条目闭环，以及对这个闭环的实测。
