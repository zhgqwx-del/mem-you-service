## 2 七模块与当前职责的对应

| 文章模块 | 当前方案对应 | 评估与取舍 |
|---|---|---|
| User | 产品前端/BFF、身份授权、可靠输入 | 已覆盖；用户文本提供内容，可信身份与权限来自服务端 |
| Agent | 主模型、可信Runtime、记录应用 | 已覆盖；模型理解与可信编排分工，不能合为模型自主控制 |

职责依据：[00§2](../docs/spec-v1/00-boundaries-and-invariants.md#2-系统职责)、[00§4.1](../docs/spec-v1/00-boundaries-and-invariants.md#41-memoryservice内部逻辑分层)、[03§2.1](../docs/spec-v1/03-agent-sequences-and-recovery.md#21-目标生命周期)。

### 三路信息来源与内部检索通道

文章的“三路”回答Agent从哪里取得信息；本服务的近期、中文词法、dense、实体/类型通道回答如何在获授权来源与记忆中找证据。这两个问题处于不同层面。

| 信息来源 | 主要责任方 | 在当前设计中的边界 |
|---|---|---|
| 当前会话与执行状态 | Runtime、产品/Agent journal | 原消息、任务进度、工具结果和未知执行结果由宿主管理；恢复不能靠语义召回猜测 |
| 跨会话个人记忆 | MemoryService及MemoryAdapter | 返回有来源、版本和失效依赖的陈述、偏好、约束等，支持精确取证 |
| 外部知识与业务当前值 | 获授权知识/产品工具 | 文档检索与产品metrics有各自权限和当前性；精确统计仍读正式业务系统 |

互不依赖的读取可以在宿主按预算编排，但文章不能证明所有请求都需要三路，也不能证明一律并行最佳。执行上下文取决于主体、授权和前序回执时，仍按真实依赖排序。任何进入full_lifecycle宿主的Memory正文都须保留依赖，不能经工具结果或摘要绕开清理。

### 分类维度的澄清价值

文章较好地区分了多种分类，可以保留这一讲法：短期/长期描述会话范围；语义/情景/程序描述内容性质；结构化/非结构化描述表达形式；关系库/向量索引/图描述存储或检索技术。L0–L3则描述本服务的数据处理职责。这些维度可以交叉，无需增加第五层或四套记忆库。

文章将外部知识库列为常见信息载体有助于理解整体Agent，但RAG是检索增强生成方法，也可以用于个人记忆召回；不应把“RAG只能处理外部知识”作为硬边界。是否属于个人记忆仍取决于来源、用途、作用范围及生命周期。

## 3 两条流程中需要保留的差异

### 召回触发与请求顺序

文章的“理解意图→判断是否检索→生成查询→检索→融合→组包→执行”适合讲解。当前产品的可实施顺序还需保留可靠接收与使用门禁：

1. 可信宿主先可靠接收输入，固定operation和planned source/group；原生item持久后再绑定origin。原item身份未就绪时沿原计划可靠排队，不提前发布镜像；已确认picker的正式提交不等待身份补齐或记忆服务。镜像失败沿同一journal计划补送，不丢输入或重复创建业务记录。
2. MemoryAdapter持久本轮决策。自由理解、指代或消歧需要时，在首模型前prepare；主体尚不明确按既有规则待补，不猜本人或扩大范围。已确认且保存/回应均不依赖历史的picker可明确skip。
3. 服务按授权、主体、时间、必要约束及预算召回；允许无关历史不交付。主Agent需要时用受控工具精确补查。
4. 宿主在模型step、相关工具执行和交付前校验实际依赖，按可信业务回执区分已接收、已保存和记忆应用状态。

因此，关键词、相似度或额外模型可以作为未来策略实验，不能成为绕过适用约束的许可。特别是“没有说上次/之前”不证明没有历史依赖。首发不增加前台LLM Query Rewrite/Expansion、规划或摘要调用，继续使用[04§1](../docs/spec-v1/04-evaluation-and-acceptance.md#1-v1-检索实现基线)既定基线；替换算法须通过版本化实验。

### 可靠来源与选择性派生

文章强调先提取值得保存的内容，再分类、写入和维护。该思路适用于L1派生筛选；当前服务须保持[00§4.1.1](../docs/spec-v1/00-boundaries-and-invariants.md#411-各层的构建与维护机制)的区别：

- **来源接收**按授权、稳定身份、角色及生命周期可靠保存，不能由模型显著性判断决定是否丢弃。
- **派生记忆**可由LLM提出注册schema内候选，程序校验可检查的来源、字段、主体、版本和人工保护；语义忠实性另由固定评测验证。
- **正式结果**在RecordService提交后经同一有序事件镜像；助手回答或工具参数不证明提交成功。
- **索引与维护**可异步落后，明确更正和失效先限制旧依据；自动摘要、定向复核及巩固按实际启用能力执行。

这也意味着“回答完成后再保存有价值的信息”不能成为原输入和正式回执的唯一写入时机。当前已确认picker的正式保存不等待记忆服务，可靠来源计划及重送责任仍保留。

### 冲突与维护

文章的全局Python偏好与当前Java项目要求，可以说明不同作用范围的陈述能够同时有效；不能把它们简单合并或按最新一条覆盖。在当前产品中，更直接的例子是“以后回复简短”和“这一次详细解释”，后者不自动改掉长期偏好，现行[00§4.1.2](../docs/spec-v1/00-boundaries-and-invariants.md#412-用偏好变化串联四层)已有此规则。

[01§5.3](../docs/spec-v1/01-data-model.md#53-关系冲突和语义去重)另区分纠错、真实状态变化和新事件。两次相同饮水记录可能是两杯水，语义相似不能充当事件身份。反复反馈可以形成待核验候选，但模型置信度、出现次数或被引用次数不把推断变成明确确认，也不能覆盖人工管理的记忆头。

文章的过期清理、时间衰减与重复合并要按这些边界理解：排序变低不等于失效，低频不等于可以删除，待复核不等于硬过期。来源、有效记忆和控制记录继续按[04§8](../docs/spec-v1/04-evaluation-and-acceptance.md#8-运维-保留期与恢复验收)保留与清理，不能用遗忘曲线替代用户授权和删除规则。

## 5 优化建议与采纳情况

以下三项已在现行分册细化，沿用既有能力、验收ID与门槛；实际夹具、诊断报告和效果结果待实现阶段交付。

### 说明信息来源和分类维度

用本文第2节的对照解释“会话状态、个人长期记忆、外部知识”归谁负责，并区分范围、内容类型、表达和存储技术。已补入[00§4.1.3](../docs/spec-v1/00-boundaries-and-invariants.md#413-agent信息来源与记忆分类维度)，不新增组件、公共scope或schema。

### 选取少量能暴露错误的夹具

首次建立评测资产时，从既有G类场景、C/A合同用例及writer对照中选以下代表变体；不是新一轮验收编号或新增首发能力：

| 夹具变体 | 要定位的问题 |
|---|---|
| 明确主体的自由输入没有“之前”等关键词，但存在适用约束 | 触发器是否错误skip，必要约束是否被普通相关性排序遗漏 |
| 长期简短偏好、本轮详细要求、后来明确改为长期详细 | 是否分清临时作用范围和长期修订，是否及时停用旧依赖 |
| 多次要求详细但未表达长期偏好，随后人工改为简短 | writer是否擅自升级确认、过度归纳或覆盖人工头 |
| 内容相同的两次饮水，与明确指向同一杯的更正 | 是否把新事件误合并，是否正确处理更正目标及来源身份 |

已有依据为00§4.1.2、01§5.3、04的W/G场景、§5.2及§6.4.1，固定变体已补入[04§5.5](../docs/spec-v1/04-evaluation-and-acceptance.md#55-记忆触发偏好与事件身份的固定变体)。人工保护使用固定来源/记忆身份和CAS，不要求跨来源自动识别合并偏好。样本只使用当时可见的授权来源前缀，开发集和封存测试集分开，不能用后续提问反向指导历史写入。

### 把反馈落到可审查的错误归因

复用[01§9.3](../docs/spec-v1/01-data-model.md#93-审计和评测日志)与04§6.3–6.4.1，按类别定位一次失败：错误skip、writer候选错误、索引/召回遗漏、融合或预算淘汰、交付后reader误用，或源当前性/权限/失效问题。合法L0原文可以直接检索，writer候选不是所有读取的前置；控制链问题也不能作为排序误差处理。

随后选择修复对象：补夹具、改抽取提示、调检索或门控、改工具定义/代码，只有有证据且适用的内容才进入记忆修订。先用人工可审查报告实施诊断，不要求自动挖掘全部Trace或采集真实用户轨迹。

该流程已在[00§4.5.3](../docs/spec-v1/00-boundaries-and-invariants.md#453-反馈诊断与受控修订)说明，分项诊断和报告口径见[04§6.3.1](../docs/spec-v1/04-evaluation-and-acceptance.md#631-反馈诊断与修复报告)；不新增公共日志字段或自动学习任务。

## 6 当前不宜据此扩展的内容

- 不新增独立Memory Trigger/Manager微服务，不为分类名称引入Redis、Elasticsearch或图数据库。
- 不把项目/组织共享记忆当作现有owner授权的隐含能力；出现真实需求时再设计作用域、授权与生命周期。
- 不把工作流执行进度迁入记忆事实库，也不让记忆召回推断未知工具结果或自动补写正式记录。
- 不把执行经验或检索正文自动提升为system指令、代码或技能。程序性经验若以后接入，需要单独明确工具/代码版本、证据、适用范围与发布验证，参见[既有研究边界](anthropic-agent-memory-review.md#用户记忆与agent执行经验)。
- 不因文章的持续优化建议提前开启全库扫描、自动学习或定期反思。[06§7.3](../docs/spec-v1/06-history-ingestion-and-repair.md#73-定向派生复核c扩展)的定向复核仍属C；A的可靠重试、明确更正和失效不后置。

当前可继续沿现行D1–D4实施。文章值得作为讲解与夹具来源收藏；方案是否有效，仍由固定数据、真实接入、中文质量、成本及恢复结果决定。
